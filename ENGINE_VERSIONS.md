# Версии движка D&D World

Этот документ фиксирует развитие единого игрового движка, а также отделяет
номер продукта от версий форматов данных и одноразовых миграций. Канонической
историей считается ветка `main` на GitHub. Если локальный коммит имеет другое
SHA, но то же дерево, тег ставится на канонический коммит из `main`.

## Что именно версионируется

### `ENGINE_VERSION`

Пользовательская версия целого движка. Она отражается в интерфейсе, журнале
аудита и описании GitHub Release. Изменение `ENGINE_VERSION` само по себе не
запускает миграции и не определяет совместимость сохранений.

Рекомендуемое объявление:

```js
const ENGINE_VERSION = '4.6';
```

### Версии схем

Версии схем описывают конкретный формат данных, а не выпуск сайта:

- `GAME_MECHANICS_SCHEMA_VERSION` — общий контракт `mechanics`;
- `ROLL_FORMULA_SCHEMA_VERSION` — контракт формул и вводимых результатов;
- `ITEM_SCHEMA_VERSION` — структура предметов и экземпляров инвентаря;
- `SPELL_PREPARATION_STATE_VERSION` — состояние книги и подготовки заклинаний.

Схема повышается только при несовместимом изменении соответствующего формата.
Один выпуск движка может не менять ни одной схемы или менять несколько схем.
Проверка записи должна опираться на нужную версию схемы, а не на
`ENGINE_VERSION`.

### Идентификаторы миграций

Каждая миграция получает отдельный неизменяемый ID и выполняется идемпотентно:
повторный запуск не должен повторно расходовать, удалять или дублировать данные.
ID описывает преобразование, а не текущую версию приложения, например:

```text
structured-cloud-rollout-20260810-v1
spell-preparation-state-v3
item-canonical-identities-v5
legacy-item-mechanics-v1
```

Существующий `structured-engine-4.1-20260810` фактически является ID старой
облачной миграции. Его необходимо сохранить для совместимости, но не
использовать как текущую версию движка и не переименовывать при выпуске 4.6.

Для выпуска 4.6 используются независимые миграции
`items-v7-unique-runtime-20260811`, `spells-v6-semantic-save-tags-20260811` и
`combat-loadouts-v2-unique-items-20260811`. Число `v7` в первом ID — порядок
rollout предметных данных, а не версия схемы: предметный контракт остаётся v6.

К 4.6 литературные описания и цветные теги остаются представлением для
человека и поиска. Боевой и предметный контуры исполняют только структурные
поля. Парсинг текста допустим как ограниченный адаптер импорта старых данных,
но не как источник последствий во время игры.

## Статус старых pull request

### PR #1 — «Синхронизировать движок эффектов заклинаний»

Статус: **superseded**. Нужные возможности функционально перенесены в `main`
коммитом `85f2461` и позднее расширены версиями 4.0–4.6. Прямое слияние старой
ветки небезопасно: её база устарела, патч конфликтует с современной
архитектурой и содержит внутренние случайные броски, запрещённые текущими
инвариантами. После статусного комментария PR следует закрыть без слияния.

### PR #2 — «Улучшить разбор эффектов заклинаний и способностей»

Статус: **superseded**. Полезные случаи разбора и тесты были перенесены
коммитом `85f2461`. Начиная с 4.0, парсер является только миграционным
адаптером, а `mechanics` — единственным источником исполняемых правил. Прямое
слияние вернуло бы зависимость игрового результата от текста. После
статусного комментария PR следует закрыть без слияния.

Если в старом PR обнаруживается ещё актуальный сценарий, он переносится в
новый тест и минимальный патч от современной `main`, а не извлекается слиянием
всей устаревшей ветки.

## Правила новых PR и релизов

1. Ветка создаётся только от актуальной GitHub `main`. Локальная ссылка
   `origin/main` сначала обновляется; ветка с эквивалентным деревом, но другой
   историей коммитов, не используется как основание PR.
2. Версионное изменение открывается как draft PR. В заголовке указываются
   версия и контур, например: `Движок 4.6: полная интеграция предметов`.
3. Описание PR фиксирует контракт данных, миграции, пользовательские сценарии,
   риски совместимости, тестовое покрытие и результаты проверки живого сайта.
4. Логика действия соблюдает последовательность
   `проверка → единый коммит ресурсов → последствия`. Отмена или ошибка до
   коммита не меняет кампанию.
5. Для каждого нового или мигрированного предмета должно существовать
   структурированное автоматическое действие либо явный `manualNote`. Кости,
   расходы и эффекты не извлекаются из `desc`, `props` или тегов во время игры.
6. Миграция сохраняет идентичность ссылок, количество, оценочную стоимость,
   заряды, экипировку, заметки и вложенное содержимое. Повторный запуск даёт
   тот же результат.
7. До слияния обязательны:

   ```bash
   node --test tests/*.test.*
   git diff --check
   ```

   Дополнительно выполняются аудит целостности базы, проверка дублей и ссылок,
   сценарии расходования ресурсов и реальные безопасные проверки интерфейса
   опубликованного сайта.
8. После слияния точный merge SHA получает аннотированный тег
   `engine-v4.6`. Для исправлений без изменения контракта используются
   патч-теги `engine-v4.6.1`, `engine-v4.6.2` и так далее.
9. Аддоны версионируются независимо, например `addon-alchemy-v1`. Версия
   движка повышается только тогда, когда аддон требует изменения общего
   контракта или среды исполнения.
10. GitHub Release создаётся из тега и содержит границы миграций, перечень
    пользовательских изменений, доказательства тестов и известные ограничения.

## Исторические теги

После проверки канонических SHA допустимо задним числом создать аннотированные
теги:

```text
engine-v4.0 -> 58ec959
engine-v4.1 -> 9f86e38
engine-v4.2 -> f5b9ec9
engine-v4.3 -> 545bf0e
engine-v4.4 -> 008fd40
engine-v4.5 -> 241152f
```

Тег 4.6 ставится только на завершённый коммит после прохождения всех проверок
и слияния соответствующего PR.
